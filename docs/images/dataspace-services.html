架構與規格邊界

圖面可水平捲動；亦可開啟 2 倍解析度 PNG。主圖以活動名稱呈現 13 條摘要連線，詳細時序見下列流程文件。

Provider 與 Consumer 是此次資料交換的角色；雙方均具有 Security Token Service、Credential Service、Decentralized Identifier Service、Control Plane 與 Data Plane。方框表示邏輯服務，分組不構成獨立部署要求。Catalogue、Vocabulary、Observability 與 Value Creation 為選用支援服務。

棕色實線彙整 DCP、DSP 與 Data Plane Signaling 互動；棕色虛線表示加入治理與管理操作。藍色粗實線表示資料內容，由 Data Source 經 Provider 與 Consumer 的 Data Plane 流向 Application。虛線框標示組織申請者、Registration System、管理 Client、Data Source 與 Application 的治理角色或外部系統邊界。各訊息的方向與先後以循序圖為準。

流程文件

  • 加入治理與 DID 準備：申請與核准、建立或沿用 DID。
  • 憑證申請與交付：CIP 受理與後續非同步 VC 交付。
  • 資料刊登與目錄存取：資料刊登與版本探索、DCP 保護的直接目錄查詢，共兩張循序圖。
  • 合約協商：Request 至 FINALIZED。
  • Pull 資料傳輸：Consumer 請求資料並通知完成。
  • Push 資料傳輸：Provider 主動傳送並通知完成，資料傳送可與啟動通知並行。

七張循序圖直接維護在 Markdown，各圖獨立編號。垂直分區以淡米色表示 Participant／Provider／Consumer、淡綠色表示 Federation Services、淡灰色表示外部系統。實線表示請求、通知或資料內容，虛線表示回應。

本架構採 Consumer 直接查詢 Provider 的受保護目錄，經 DCP 身分及 VP／VC 驗證後由 Provider 依政策回應。Holder／Verifier 由互動決定；CIP 受理不等於完成簽發。DCP 也可用於後續 DSP 互動。DID Resolution 依 DID method 實現；STS 內部 API、治理、管理與資料來源／應用整合方式依實作。

Pull 與 Push 皆由 Consumer 提出 DSP 傳輸請求，資料內容由 Provider 流向 Consumer。Push 在提供端資料流啟動後即可傳送，可能與後續啟動通知重疊。循序圖保留 Prepared／Started 的同步回應與非同步回呼分支，呈現有限資料傳輸的成功流程；例行 ACK、錯誤、重試、暫停、終止與內部驗證不展開。

規格基準

  • DSP 2025-1-err2：版本與端點探索、目錄、合約協商及傳輸流程訊息；不定義實際資料傳輸協定。
  • DCP 1.0.1：Self-Issued ID Token、Credential Issuance Protocol（CIP）與 Verifiable Presentation Protocol（VPP）。
  • Data Plane Signaling 1.0-RC4（候選版）：Control Plane 與 Data Plane 的資料流控制。
  • DID Core 1.0：DID 與文件解析；DSSC Blueprint：服務分類參考。
