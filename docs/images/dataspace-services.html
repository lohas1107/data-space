架構與規格對照

本圖直接依官方架構文件與協定規格整理。方框包含邏輯服務、內部功能及協定介面，並非必須逐一獨立部署的微服務清單。Provider 與 Consumer 是這次資料交換的角色；兩個 Participant Agent 都可以持有憑證並驗證對方。

架構邊界

  • 服務與部署：Security Token Service、Credential Service 與 Decentralized Identifier Service 是邏輯服務，可合併或分開部署。圖中 Credential Service 包含 Credential Store 的保存能力。Issuer Service 也需要自己的身分、金鑰與識別文件能力。Decentralized Identifier Service 展開了規格原名 DID Service 中的縮寫。官方系統模型。
  • 治理與信任：將 Registration System 與 Verifiable Data Registry 放入 Trust Services 是本圖的功能映射。Registration System 處理加入與成員治理，位於 Decentralized Claims Protocol 規範範圍外；Verifiable Data Registry 是識別資訊與憑證結構資訊的抽象登錄角色，不等於成員資料庫，也不要求單一中央服務。信任模型。
  • 角色與政策：Provider／Consumer 與 Holder／Verifier 是不同角色軸。圖中依這次交換分別顯示目錄發布與查詢，沒有要求 Consumer 發布資料目錄。Policy Administration and Evaluation、整合與驗證方框是功能分組；憑證驗證亦會發生於 Credential Service 等接收受保護請求的元件。Dataspace Protocol 本身不強制使用 Decentralized Claims Protocol，本圖選擇將兩者組合。協定關係。
  • 版本探索：Protocol Version Metadata Endpoint 對應 /.well-known/dspace-version。Dataspace Protocol 要求這個端點不加版本且不要求驗證；即使只支援一版仍須提供，並不代表必須支援舊版。共同要求。
  • 既有系統：Data Source 與 Application 放在服務區外表示整合邊界；Data Plane 可與既有端點或應用整合。一般消費端應用不自動歸類為 Value Creation Services；底部呈現的是可依使用情境提供的服務示例。服務定義。
  • 實作規格：還需選定憑證 profile、識別方法、政策語意與資料傳輸 profile，並依對應規格驗證訊息、狀態機、存取授權與錯誤處理。這張圖提供元件責任與互動邊界，不能取代協定符合性驗證。憑證 profiles。
