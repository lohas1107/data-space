# data-space Constitution

## Core Principles

### I. PoC 驗證優先

本專案為概念驗證（PoC）。規格、設計與實作 MUST 以驗證當前需求與可行性為優先，
並採用足以完成驗證的簡單方案。新增抽象層、基礎設施或正式營運規格時，
MUST 說明其與當前驗證目標或使用者明確需求的關聯。
此原則用於縮短驗證迭代，避免尚未成立的未來需求增加實作成本。

### II. 向後相容依明確需求處理

除非使用者特別要求，向後相容 MUST NOT 被視為預設的優先目標或必要驗收條件。
當保留舊有 API、資料格式、設定或行為會增加複雜度或延誤 PoC 驗證時，
可採用破壞性變更，無須預設提供相容層、雙版本支援或棄用期。
變更說明 MUST 記錄受影響的使用方式，以及需要的更新或重建步驟（如有）。
使用者明確要求相容性時，MUST 在該功能規格中記錄適用範圍，並將其納入驗證。

### III. 官方開源套件優先

新增依賴或選擇實作方案時，MUST 優先評估相關技術的原專案或官方組織維護、
且以開源授權發布的套件。官方文件僅推薦的第三方套件，不視為官方維護套件。
若官方開源套件能滿足當前 PoC 需求，MUST 優先採用其既有能力，避免重複實作。
若不存在適用套件，或其功能、授權、整合成本不適合當前需求，
可採用其他開源套件或自行實作，並 MUST 在技術決策中簡述原因。
此原則用於減少自製維護成本，並讓整合方式與上游專案保持一致。

### IV. 以具體實例與活文件驗證 PoC

每項 PoC 驗證目標 MUST 採用 Specification by Example（以實例描述規格），
在實作前以領域用語定義具體實例，作為需求理解與驗收的共同依據。
每個實例 MUST 包含明確的前置條件、具體輸入資料、操作，以及可觀察的預期結果；
可使用 Given／When／Then 或範例表格，不限定工具或語法。
實例 MUST 涵蓋主要成功情境，以及會影響可行性判斷的邊界與失敗情境；
若某類情境不適用，MUST 記錄理由。

上述實例 MUST 作為活文件（Living Documentation）與程式碼一同版本管理，
並以穩定識別碼或連結串接驗證目標、自動化測試、執行方式與驗證結果。
每個用於驗收的實例 MUST 對應可重複執行的自動化測試，
由測試執行具體輸入與操作，並透過自動斷言判定可觀察的實際結果是否符合預期。
測試 MUST 納入專案測試流程，記錄執行指令、必要環境與測試資料準備方式，
以便在後續變更時重新執行。
單次手動操作、人工比對結果或僅有操作紀錄 MUST NOT 取代活文件的自動化驗證。
自動化尚未完成或測試無法執行時，MUST 記錄未完成或受阻原因，
並將對應目標標示為尚未驗證成功，不得以成本或腳本限制改採手動驗收。
本原則不要求額外導入特定 BDD 框架、文件平台或測試基礎設施。

影響行為的變更 MUST 在同一變更中同步更新受影響的實例、自動化測試與驗證結果。
活文件的驗證狀態 MUST 以對應自動化測試的實際執行結果為依據。
活文件 MUST 區分預期結果與實際結果，記錄驗證日期、受驗證的程式版本，
以及通過、失敗、未執行或受阻狀態；失敗與受阻 MUST 註明原因。
過期或未執行的結果 MUST NOT 作為目前版本已驗證的證據。
此原則讓 PoC 的可行性結論建立在可持續重跑、自動判定的行為證據上，
並避免規格文件與實際行為脫節。

### V. 重現用腳本依明確需求新增

除非使用者特別要求，MUST NOT 在專案內新增專供重現驗證步驟、實驗或結果的腳本
（script）。一般的 PoC 驗證、自動化或活文件要求 MUST NOT 視為新增此類腳本的要求。
納入專案測試流程、具有自動斷言且用於持續驗證行為的測試程式與必要測試資料，
屬於原則 IV 要求的自動化測試，可依驗證需求新增或修改，無須使用者另行要求。
此類測試 MUST NOT 視為本條限制的額外重現用腳本。
自動化測試 MUST 優先沿用既有測試工具與執行指令，並以活文件記錄實例與測試結果；
可重現性的文件與證據要求 MUST NOT 衍生為必須新增或提交重現用腳本的驗收條件。
使用者明確要求新增此類腳本時，MUST 在該功能規格或任務中記錄用途與範圍。
此原則用於控制 PoC 的維護成本，避免為保留驗證過程而增加未被要求的專案產物。

## 專案範圍與技術取捨

- PoC 定位本身不構成正式營運所需的相容性、可用性或擴充性承諾；
  明確提出的功能與品質需求仍 MUST 滿足。
- 技術選型 MUST 以當前驗證需求為依據；本憲章不預先指定語言、框架或部署平台。
- 套件選型說明 MUST 記錄採用的套件、維護來源與開源授權；
  偏離官方開源套件優先原則時，附上取捨理由即可，無須另設核准程序。

## 開發與審查流程

- 規格 MUST 說明本次 PoC 要驗證的結果，並依原則 IV 定義具體實例與通過條件；
  使用者另有相容性要求時，明列其範圍並納入實例。
- 設計與任務審查 MUST 確認每項驗證目標均有對應實例、自動化測試與執行方式、
  新增複雜度服務於當前需求，並檢查套件選型是否符合原則。
- 規劃或審查新增重現用腳本時，MUST 確認有使用者的明確要求及已記錄的用途與範圍；
  活文件所需的自動化測試依原則 V 可直接新增或修改。
- 完成變更時，MUST 執行受影響實例所對應的自動化測試，將測試結果與證據連結回活文件，
  並記錄已知限制與受影響的使用方式。
- 宣告某項 PoC 目標驗證成功前，其主要成功情境與影響可行性判斷的邊界、
  失敗情境所對應的自動化測試 MUST 全部通過，且證據對應本次受驗證版本。
  任一必要實例失敗、未執行或受阻時，MUST 明列該目標尚未驗證成功及其原因；
  預期的錯誤處理符合實例所定義的結果時，該實例屬於通過。

## Governance

本憲章作為專案規格、計畫、任務與實作審查的共同依據。
使用者針對特定功能明確提出的需求 MUST 優先適用，並記錄於該功能文件；
其中向後相容性要求屬於原則 II 已允許的例外，無須為單一功能修改憲章。

修訂全專案原則時，MUST 更新本文件、說明修訂理由與影響，
同步更新頂端 Sync Impact Report、版本及最後修訂日期。
原始通過日期維持不變；既有且仍適用的專案決策 MUST 保留。

憲章版本採語意化版本：不相容的治理變更、原則移除或重新定義升 MAJOR；
新增原則、章節或實質擴充指引升 MINOR；僅文字澄清與非語意修正升 PATCH。
此版本規則用於治理文件，不代表 PoC 的應用程式必須承諾向後相容。

每次規格、計畫與變更審查 MUST 檢查本憲章的適用條款。
不符合條款時，MUST 調整方案、記錄條款允許的取捨，或依使用者新指示修訂憲章。
